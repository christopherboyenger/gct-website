# GCT Daily — Automation Architecture

## Objective

Turn the GCT website newsroom into a repeatable media + intelligence engine without allowing AI to publish unverified external claims autonomously.

The operating rule is simple:

**Discovery is automated. Verification is automated. Drafting is automated. Publication requires human approval.**

In phase one, GitHub is the editorial queue. **Merging an automated editorial PR is the publish action.**

---

## Phase 1 — Implemented in this branch

### 1. Discovery

`data/news/sources.json` contains discovery feeds focused on:

- creator economy
- brand partnerships and sponsorships
- major golf brand business moves
- golf technology and startups
- golf media
- funding / M&A / investment
- golf travel and destinations
- creator golf events

The initial feeds use Google News RSS as a discovery layer. These feeds are **not** treated as publication authority.

### 2. Deterministic triage

`scripts/news/ingest.mjs`:

- fetches discovery feeds
- ignores stories older than the configured freshness window
- strips obvious duplicates
- ignores stories already published by GCT Daily
- scores stories using creator, sponsorship, brand, media, technology, travel, event, executive and money signals
- penalizes generic scoring, betting, injury and tournament-result noise
- writes the ranked candidate set to `.newsroom/candidates.json`

The deterministic first pass reduces AI cost and keeps the verifier focused on the strongest candidates.

### 3. AI verification + drafting

`scripts/news/draft.mjs` uses the OpenAI Responses API with web search and Structured Outputs.

For each high-scoring candidate it must:

- independently search the web
- find an authoritative primary source **or** at least two credible independent sources
- reject rumors, source conflicts, repost-only claims and unverifiable details
- classify the story into the GCT editorial taxonomy
- draft:
  - headline
  - dek
  - What Happened
  - Why It Matters
  - The GCT Take
  - article body
- return the exact source URLs used
- identify relevant entities
- optionally extract commercial signals after the editorial decision

The script independently enforces the source rule after the model responds. A model saying a story is verified is not sufficient by itself.

### 4. Editorial proposal

`scripts/news/publish.mjs` appends only verified drafts to `news-data.json` and makes the strongest new story the lead story.

It also generates `.newsroom/pr-summary.md`, which contains:

- verification confidence
- discovery score
- source links
- proposed framing
- internal partnership signals
- any do-not-contact / competitor caution generated by the review

### 5. Human approval

`.github/workflows/gct-news-scout.yml` runs four discovery sweeps per day and can also be run manually.

If no story clears the threshold, it exits without creating a PR.

If one or more stories clear the threshold, it creates an `automation/gct-daily-*` branch and opens an editorial review PR.

**Merging that PR publishes the stories.**

The workflow never merges its own PR.

### 6. Audit trail

Every workflow run uploads `.newsroom/` as a private GitHub Actions artifact for 14 days, including candidates, verification results and the generated review summary.

## Required repository configuration

### GitHub Actions secret

Add:

`OPENAI_API_KEY`

under:

**GitHub → gct-website → Settings → Secrets and variables → Actions → Repository secrets**

The key must never be committed to the repository.

### Optional repository variable

`OPENAI_MODEL`

If omitted, the pipeline uses the model configured in `data/news/editorial-policy.json`.

### GitHub Actions setting

The repository must allow GitHub Actions to create pull requests:

**Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests**

The workflow only creates PRs; it does not approve or merge them.

---

## Editorial thresholds

Configured in `data/news/editorial-policy.json`.

Initial settings:

- candidate freshness: 96 hours
- heuristic threshold: 55/100
- verification threshold: 80/100
- maximum proposed stories per run: 3
- source standard: one authoritative primary source OR two independent credible sources

These should be tuned after observing 1–2 weeks of real candidate data.

# Phase 2 — Newsletter + distribution engine

Trigger: merge to `main` when `news-data.json` changes.

### Newsletter

Recommended flow:

1. detect newly published stories
2. assemble the daily edition
3. create a **draft** newsletter in Beehiiv
4. human review inside Beehiiv
5. send or schedule

Start with draft creation rather than automatic send. Once quality is consistent, daily editions can be scheduled automatically while breaking / sensitive items remain approval-only.

Suggested edition format:

- Lead Story
- 3–5 Things Worth Knowing
- Creator Move
- Brand Move
- Money / Tech
- The GCT Take
- Creator to Watch or GCT Data

### Social repurposing

For each approved story generate:

- LinkedIn post
- X post / short thread
- Instagram caption
- Instagram carousel outline
- optional short-form video script

Do not auto-post in the first rollout. Put these in a distribution queue and approve them independently of the article.

# Phase 3 — Brand / creator intelligence database

The publication becomes more valuable when every verified story also creates structured intelligence.

Recommended dedicated database entities:

### `news_sources`
Trusted sources and reliability metadata.

### `news_candidates`
Raw discovered items, dedupe fingerprints, source and scores.

### `news_stories`
Draft / approved / published status, copy, sources and timestamps.

### `entities`
Brands, creators, people, courses, resorts, media companies, technology companies and organizations.

### `story_entities`
Many-to-many relationship between stories and entities.

### `commercial_signals`
Structured signals such as:

- new creator campaign
- new sponsorship budget
- product launch
- creator signing
- destination opening
- funding / acquisition
- new marketing executive
- media expansion
- event activation

### `partnership_opportunities`
A separate commercial assessment with status, owner, priority and outreach decision.

**Important:** editorial relevance must never depend on whether the entity is a potential GCT customer.

A dedicated database is preferable to coupling this newsroom to the existing GCT app database. The currently connected Supabase project named `GCT` was inactive when this architecture was created, so phase one deliberately does not modify or reactivate it.

# Phase 4 — GCT newsroom command center

Once the database exists, replace GitHub-as-editor with a private web dashboard.

Suggested columns:

**Inbox → Verified → Drafted → Needs Review → Approved → Published → Distributed**

Each card should show:

- headline
- category
- freshness
- relevance score
- verification confidence
- source list
- primary source badge
- entities
- partnership signal
- competitor / do-not-contact warning

Actions:

- Approve
- Edit
- Reject
- Hold
- Publish now
- Schedule
- Create newsletter
- Create social package
- Send to partnership pipeline

GitHub remains the source of website code; the database becomes the newsroom state machine.

# Phase 5 — Proprietary GCT intelligence

This is the defensibility layer.

Add first-party reporting and data products that outside publications cannot easily reproduce:

- fastest-growing golf creators
- creator engagement benchmarks
- sponsorship activity by brand
- campaign category trends
- creator event calendar
- creator-brand deal tracker
- GCT leaderboard trends
- creator geography / audience insights
- quarterly Golf Creator Economy Report

Public stories can surface selected insights. Full datasets and reports can become sponsor inventory, premium research, lead magnets or member benefits.

# Commercial flywheel

A verified story can create multiple outputs without compromising editorial independence:

`NEWS EVENT`

→ GCT Daily story

→ newsletter item

→ LinkedIn / X / Instagram content

→ entity record

→ commercial signal

→ partnership opportunity assessment

→ potential brand conversation

The publication therefore creates **attention**, **first-party audience**, **industry intelligence**, **relationship surface area**, and **qualified partnership signals** from the same underlying research process.

# Guardrails

1. No autonomous publishing of external factual stories in phase one.
2. No publication from a discovery aggregator alone.
3. No fabricated quotes, figures, dates, titles or deal terms.
4. No hidden advertorial. Sponsored editorial must be labeled.
5. Editorial coverage does not imply a sales target.
6. Competitors may be covered editorially; that does not mean GCT should contact them commercially.
7. Internal commercial signals are not displayed publicly.
8. Source links remain attached to the story data for auditability.
9. Human review remains mandatory for legal disputes, allegations, politics, safety issues, confidential information and sensitive claims.
10. If verification quality is uncertain, reject the story rather than publish first and correct later.
